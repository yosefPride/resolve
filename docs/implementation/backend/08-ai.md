# Backend — AI

Covers `src/ai/`: `models.rs` (283), `repository.rs` (302), `client.rs` (401), `service.rs`
(536), `handlers.rs` (149), `mod.rs` (5).

The only module that talks to an external service. Every other module's interesting parts are
about enforcing isolation and RBAC against MongoDB; this one's are about **not calling Gemini
more than necessary** (the caching layer, for summarize/analyze/report) and **never letting a
network failure or a hallucination reach the client as anything but a clean `ApiError`**.

Six endpoints, all under `/ai/...`, all `GroupScoped`:
`POST groups/{id}/tickets/{ticket_id}/summarize`, `.../analyze` (member of `{id}`),
`POST groups/{id}/report` (Group Admin only — `GroupScoped` proves membership, `AiService`
itself upgrades the check), and `POST`/`GET`/`DELETE groups/{id}/tickets/{ticket_id}/chat`
(member of `{id}`, confirmed with user: 10 messages/hour per user, and scoped only to this app's
bug-tracking work — see `chat_prompt` below).

Chat is a deliberate exception to "don't call Gemini more than necessary": every message is a
genuinely new request, so unlike the other three endpoints there is no cache check to make —
only a rate limit.

## `ai/models.rs`

### `struct TicketSummaryResponse { summary, cached: bool }` / `struct TicketAnalysisResponse { severity_prediction, suggested_fix, classification, cached: bool }`
API response shapes. `cached` is not in `docs/specification/api.md`'s field list — added
because it's cheap, and it's what `ai_service_tests.rs` asserts on to prove a cache hit
skipped the Gemini call.

### `struct AiTicketInsight`
Stored document: `id`, `group_id`, `ticket_id`, `summary: Option<String>`,
`summary_source_updated_at: Option<BsonDateTime>`, `severity_prediction`, `suggested_fix`,
`classification` (all `Option<String>`), `analysis_source_updated_at: Option<BsonDateTime>`,
`created_at`, `updated_at`.

**One document per ticket**, upserted in place — `docs/specification/database.md`'s "1-to-1 or
1-to-many over time" resolves to 1-to-1 here, with "over time" being this document's fields
filling in as `summarize`/`analyze` each run independently.

**Two separate freshness timestamps, not one.** `summary_source_updated_at` and
`analysis_source_updated_at` each snapshot `ticket.content_updated_at` at the moment that field
group was last generated. They have to be independent: `summarize` and `analyze` are separate
calls, so an edit can invalidate one without the other ever having run — a single shared
fingerprint would let a stale field read as fresh just because the *other* field was
regenerated more recently.

`content_updated_at` (not the ticket's plain `updated_at`) is the fingerprint — see
`05-tickets.md`'s equivalent note and `ticket/models.rs`'s doc comment. It's bumped by
`TicketService::update_ticket` only when title/description/priority change, **not** status —
closing or reopening a ticket doesn't touch anything the AI reads, so it shouldn't throw away a
still-accurate cached summary/analysis.

### `fn is_summary_fresh(&self, ticket_content_updated_at) -> bool` / `fn is_analysis_fresh(...)`
Pure, no I/O: `field.is_some() && source_timestamp == Some(ticket_content_updated_at)`. Both
conditions matter — `is_some()` catches "never generated", the timestamp match catches "stale
since regenerated". Four inline tests cover fresh / stale-after-edit / never-generated /
partially-generated.

### `struct PriorityBreakdown { low, high, critical }`
Ticket counts by priority, used in the group report.

### `struct ReportData { total_tickets, open_tickets, closed_tickets, priority_breakdown, recent_tickets_7d, narrative }`
The typed shape behind `AiGroupReport.report_data` (a raw `Document` in Mongo —
`docs/specification/database.md` doesn't pin its schema). Always round-tripped through this
struct via `bson::to_document`/`bson::from_document` in `AiService::generate_group_report`
rather than hand-rolled `doc!` key access.

`docs/specification/api.md`'s report endpoint returns "group-wide analytics, ticket trends,
workload distribution." There's no assignee/owner field on `Ticket` (only `created_by`,
`status`, `priority`), so **"workload distribution" is read as ticket volume across
priority/status**, not per-person load — `total_tickets`/`open_tickets`/`closed_tickets`/
`priority_breakdown` are that. `recent_tickets_7d` (tickets created in the last 7 days) stands
in for "trends." `narrative` is where Gemini turns those hard numbers into 2-4 sentences of
prose — see `client.rs`'s `narrate_report` below for why the model never does the counting.

### `struct GroupReportResponse { #[serde(flatten)] data: ReportData, generated_at, cached }`
API response shape: `ReportData`'s fields flattened alongside `generated_at`/`cached`.

### `struct AiGroupReport`
Stored document: `id`, `group_id`, `report_data: Document`, `generated_at`, `generated_by`.

**One new document per generation**, unlike `AiTicketInsight`'s single upserted-in-place doc —
`docs/specification/database.md`: "groups → ai_group_reports (**1-to-many**)". So
`find_latest_report` always reads the newest one, and older reports persist as history (until
the TTL index reaps them — see `db/indexes.md`).

### `fn is_fresh(&self, now, ttl_millis) -> bool`
`now.timestamp_millis() - self.generated_at.timestamp_millis() < ttl_millis`. The report
cache's mechanism is deliberately different from the ticket insight's: instead of invalidating
on a precise content change (which for a *group* would mean tracking every ticket's
`content_updated_at`, expensive to check), it just expires after a fixed window —
`docs/specification/ai-integration.md`'s "cached for a period of time." The window is one hour,
confirmed with the user rather than picked unilaterally. Three inline tests cover
within-TTL / past-TTL / the exact-boundary instant.

### `enum ChatRole { User, Assistant }`
`#[serde(rename_all = "snake_case")]`, same pattern as `TicketStatus`/`TicketPriority`.
"assistant", not "ai"/"gemini" — keeps the field provider-agnostic, same reasoning as
`AiProvider` being a trait rather than a concrete `GeminiClient` type.

### `struct ChatMessage`
Stored document: `id`, `group_id`, `ticket_id`, `role: ChatRole`, `user_id: Option<ObjectId>`,
`content`, `created_at`.

**One document per message** — unlike `AiTicketInsight`'s single upserted-in-place doc, a
conversation is inherently a sequence. Structurally closest to `comment::models::Comment` (same
`group_id`/`ticket_id` scoping, same insert-only oldest-first list shape), not to anything else
in this module. `user_id` is `Some` for a user message and `None` for an assistant message —
`AiRepository::count_recent_user_messages` filters on both `role` and `user_id` being present to
count one user's own messages for the rate limit.

There is exactly **one ongoing conversation per ticket** — no separate conversation/thread id.
"New chat" (`AiService::clear_chat`) just deletes every message on the ticket's thread rather
than archiving it under a new thread id; this was a deliberate scope decision (confirmed with
user) to avoid building thread-list UI/data-model complexity for a feature that doesn't need it.

### `struct SendChatMessageRequest { message: String }`
Request body for `POST .../chat`. Derives both `Serialize` and `Deserialize` (unlike a
request-only shape that would just need `Deserialize`) so `ai_api_tests.rs` can build one to
send, same reason `CreateCommentRequest` does.

### `struct ChatMessageResponse { id, role, user_id: Option<String>, user_name: Option<String>, content, created_at }`
API shape for one message. `user_name` is enriched the same way `CommentResponse`'s is (a
`UserService` lookup in `AiService::enrich_chat_message`) — `None` for an assistant message,
same as `user_id` on the underlying `ChatMessage`. The ticket's chat is a shared, group-visible
thread like comments, not a private per-user conversation, so who asked matters once more than
one member has used it.

### `struct SendChatMessageResponse { user_message: ChatMessageResponse, assistant_message: ChatMessageResponse }`
`POST .../chat`'s response returns **both** messages, not just the assistant's reply — the
frontend would otherwise have to fabricate an id/timestamp for the user's own message to render
it immediately, and that fabricated id would never match the persisted one.

## `ai/repository.rs`

### `enum AiRepoError { Database(_) }`
Single variant, same pattern as every other repo error in the codebase. Maps to
`ApiError::Internal`.

### `struct AiRepository { insights: Collection<AiTicketInsight>, reports: Collection<AiGroupReport>, chat_messages: Collection<ChatMessage> }`
Three collections: `"ai_ticket_insights"`, `"ai_group_reports"`, `"ai_chat_messages"`.

### `async fn find_insight(&self, group_id, ticket_id) -> Result<Option<AiTicketInsight>, _>`
`find_one({group_id, ticket_id})` — same multi-tenancy query shape as
`TicketRepository::find_by_id`.

### `async fn upsert_summary(&self, group_id, ticket_id, summary, source_updated_at) -> Result<AiTicketInsight, _>` / `async fn upsert_analysis(&self, group_id, ticket_id, severity, fix, classification, source_updated_at) -> Result<AiTicketInsight, _>`
`find_one_and_update` with `upsert(true)`, `$set` on just that field group's keys plus
`updated_at`, `$setOnInsert` for `group_id`/`ticket_id`/`created_at`. Each touches only its own
field group — calling `upsert_analysis` after `upsert_summary` leaves the summary intact, and
vice versa (see `AiTicketInsight`'s doc comment on why).

### `async fn delete_by_ticket(&self, group_id, ticket_id) -> Result<u64, _>`
Cascade target for **one ticket's** deletion, mirroring `CommentRepository::delete_by_ticket`.
Called from `TicketService::delete_ticket`. Clears the ticket's insight *and* its chat thread,
combined count.

### `async fn delete_by_group(&self, group_id) -> Result<u64, _>`
Cascade target for a **whole group's** deletion, mirroring `CommentRepository::delete_by_group`.
Called from `purge_group_data` (`group/service.rs`). Clears all three collections and returns
the **combined** count — insights, reports, and chat messages are different documents but the
same cascade concern, so callers get one number instead of needing to track three.

### `async fn find_latest_report(&self, group_id) -> Result<Option<AiGroupReport>, _>`
`find_one({group_id}).sort({generated_at: -1})` — the newest report, or `None` if one was never
generated. Feeds `AiGroupReport::is_fresh`'s TTL check.

### `async fn insert_report(&self, group_id, report_data, generated_by) -> Result<AiGroupReport, _>`
Plain insert, `generated_at: BsonDateTime::now()` set here (not by the caller) — see
`service.rs`'s note on why `AiService::generate_group_report` uses *this* call's returned
`generated_at` for its response rather than a timestamp it captured itself earlier.

### `async fn list_chat_messages(&self, group_id, ticket_id) -> Result<Vec<ChatMessage>, _>`
`find({group_id, ticket_id}).sort({created_at: 1})` — oldest-first, same shape as
`CommentRepository::list_by_ticket`. `AiService` takes the tail of this (`CHAT_HISTORY_LIMIT`)
for the transcript sent to Gemini; the frontend renders the whole thing top-to-bottom as-is.

### `async fn insert_chat_message(&self, group_id, ticket_id, role, user_id: Option<ObjectId>, content) -> Result<ChatMessage, _>`
Plain insert, `created_at: BsonDateTime::now()` set here. `AiService::send_chat_message` calls
this twice per turn — once for the user's message, once for the assistant's reply.

### `async fn clear_chat_messages(&self, group_id, ticket_id) -> Result<u64, _>`
"New chat": unconditional `delete_many({group_id, ticket_id})`. There's only ever one
conversation per ticket (no thread id to scope by), so clearing it is emptying the whole
collection for that pair.

### `async fn count_recent_user_messages(&self, user_id, since: BsonDateTime) -> Result<u64, _>`
`count_documents({role: "user", user_id, created_at: {$gte: since}})` — feeds
`AiService::send_chat_message`'s rate-limit check. Scoped to `user_id` alone (no `group_id`/
`ticket_id`), across every ticket that user has chatted on: the limit is a per-user guardrail
against hammering the endpoint, not a per-conversation quota, so it can't be dodged by spreading
messages across tickets. `role` filters via `bson::to_bson(&ChatRole::User)` rather than a
hardcoded `"user"` literal, same pattern `ticket/repository.rs` uses for its own enum filters.

## `ai/client.rs`

### `const GEMINI_MODEL: &str = "gemini-flash-latest"`
A rolling alias, not a pinned version. `gemini-2.0-flash` returned `429 RESOURCE_EXHAUSTED`
with quota limit `0` during development (superseded model, no free-tier quota on this
project); `gemini-flash-latest` resolves to Google's current flash model and works. The alias
also means this doesn't need re-pinning every time Google retires a dated model name.

### `struct AnalysisResult { severity_prediction, suggested_fix, classification }`
Plain data, the client's return type for `analyze`.

### `trait AiProvider`
```rust
fn summarize(&self, title: &str, description: &str) -> impl Future<Output = Result<String, ApiError>> + Send;
fn analyze(&self, title: &str, description: &str) -> impl Future<Output = Result<AnalysisResult, ApiError>> + Send;
fn narrate_report(&self, stats_summary: &str) -> impl Future<Output = Result<String, ApiError>> + Send;
fn chat(&self, title: &str, description: &str, transcript: &str, message: &str) -> impl Future<Output = Result<String, ApiError>> + Send;
```
The abstraction that makes `AiService` testable without the network — `GeminiClient` is the
real implementation, `ai_service_tests.rs`'s `FakeProvider` is the other one. Methods are
desugared to `-> impl Future<...> + Send` rather than plain `async fn`: a plain `async fn` in a
public trait doesn't guarantee its future is `Send`, which would silently break under Actix's
multi-threaded runtime the first time a handler's `.await` needed to cross a thread.

`narrate_report` takes `stats_summary: &str` — a plain-text rendering of numbers `AiService`
already computed from `TicketRepository` data. The model's job is turning those into prose, not
counting anything itself, so a hallucinated figure can't end up in a report.

`chat` takes `transcript: &str` — same reasoning as `stats_summary`: `AiService` (via
`build_transcript`) pre-formats prior messages into a plain `"User: ...\nAssistant:
...\n..."` string (empty on the first message of a conversation) rather than this trait taking
any persistence-layer type. This trait only ever takes/returns strings.

### `struct GeminiClient { http: reqwest::Client, api_key: String }`
The real implementation. `new(api_key)` is the only constructor — no default/env-reading
inside the client itself, that's `Config`'s job.

### `async fn generate(&self, prompt, response_schema: Option<Value>) -> Result<String, ApiError>` (private)
The one method that actually calls Gemini: POSTs to
`{GEMINI_API_BASE}/{GEMINI_MODEL}:generateContent` with the API key in the `x-goog-api-key`
header (not a query param, so it doesn't end up in logs/URLs). When `response_schema` is
`Some`, sets `generationConfig.responseMimeType: "application/json"` plus the schema — this is
what makes `analyze`'s output reliably parseable JSON instead of scraped prose.
`summarize`/`narrate_report` pass `None` and get plain text back.

Any non-success HTTP status, or a `reqwest` transport error, collapses to `ApiError::Internal`
— Gemini error bodies (bad key, quota, malformed request) are never surfaced to the client raw,
same "internal errors don't leak" rule every other repo error follows.

### `impl AiProvider for GeminiClient`
Four thin wrappers around `generate` + a `parse_*` function: `summarize` →
`parse_summary_response`, `analyze` → `parse_analysis_response` (with the JSON schema),
`narrate_report` → `parse_summary_response` again (same shape as summarize: prose in, prose
out), `chat` → `parse_summary_response` again too (same shape: a short prose reply).

### `fn summarize_prompt` / `fn analyze_prompt` / `fn report_prompt` / `fn chat_prompt` (private)
Plain `format!` strings. `report_prompt` explicitly instructs the model to "use only the
numbers given — do not invent or estimate any figure not present," reinforcing what
`narrate_report`'s doc comment says structurally.

`chat_prompt` is where the "scoped to this ticket / this app's bug-tracking work only" rule
(confirmed with user) is enforced — there is no separate classifier/filter step, the prompt
instruction *is* the entire enforcement mechanism. It's stated up front, before the ticket
context, and repeated as the last line right before the new message ("New message (stay in
scope): ...") so it isn't lost to recency bias on a long transcript. The instruction tells the
model, on an out-of-scope message, to reply that it's there to help with this issue and can't
assist with unrelated requests — not to silently ignore the message or answer it anyway.

### `fn analysis_response_schema() -> Value` (private)
The `responseSchema` passed to `generate` for `analyze`: an object with three required string
fields (`severity`, `suggested_fix`, `classification`).

### `fn extract_text(body: &str) -> Result<String, ApiError>` (private)
Pulls `candidates[0].content.parts[0].text` out of Gemini's response envelope — the one shape
`summarize`/`analyze`/`narrate_report`/`chat` all share; only what's *inside* that text differs
(prose vs. a JSON string).

### `fn parse_summary_response` / `fn parse_analysis_response` (private)
`parse_summary_response`: extract, trim, reject if empty. `parse_analysis_response`: extract,
`serde_json::from_str` into a private `RawAnalysis { severity, suggested_fix, classification }`,
reject if any field is blank. Both reject rather than panic on anything malformed — a
malformed/empty Gemini response is a normal failure mode (`ApiError::Internal`), never a crash.
`chat` reuses `parse_summary_response` (same shape as `summarize`/`narrate_report`), no separate
`parse_chat_response`.

### Inline tests (14)
Four prompt-content checks (one per prompt builder) plus three `chat_prompt`-specific checks
(history section omitted when empty / included when present, the scoping instruction is
actually in the text), and the rest are `parse_*` fixture tests against a
`gemini_envelope(inner_text)` helper that builds a realistic response body — no network. Cover
the happy path plus: empty text, malformed envelope, non-JSON inner text (for analyze), missing
field, blank field.

### `tests/ai_client_live_test.rs` (separate from the inline tests)
One `#[ignore]`'d test that hits the **real** Gemini API for all four `AiProvider` methods —
`cargo test --test ai_client_live_test -- --ignored --nocapture`. Exists because the inline
tests only prove parsing logic against canned fixtures; this is what caught the
`gemini-2.0-flash` quota issue above, which no fixture-based test could have. Also makes two
`chat` calls specifically: one in-scope, and one deliberately off-topic ("What's the capital of
France?") asserting the reply doesn't actually answer it — the inline `chat_prompt` tests only
prove the instruction text is present in the prompt, not that the real model obeys it.

## `ai/service.rs`

### `struct AiService<P: AiProvider = GeminiClient> { repo, ticket_repo, user_service, rbac, provider }`
Generic over the provider, defaulted to `GeminiClient`. The default type parameter is what
keeps production call sites unchanged (`AiService::new(&state.db, &state.config)`) while
letting tests build an `AiService<FakeProvider>` via `with_provider` — the same tradeoff
`AiProvider` itself makes, one level up. `user_service` was added for chat — `enrich_chat_message`
needs it for `user_name`, the same reason `CommentService` holds one.

### `const REPORT_TTL_MILLIS` / `const RECENT_WINDOW_MILLIS`
One hour, seven days. Both plain constants, not configurable — see `models.rs`'s
`AiGroupReport::is_fresh` note on the TTL being a deliberate, confirmed-with-user choice rather
than a guess.

### `const CHAT_RATE_LIMIT` / `const CHAT_RATE_WINDOW_MILLIS` / `const CHAT_HISTORY_LIMIT`
10 messages, one hour, 20 messages. All confirmed with user, not picked unilaterally — same
"plain constant, not configurable" treatment as the report TTL above. `CHAT_HISTORY_LIMIT`
bounds prompt size/cost per turn regardless of how long a conversation has run: the *full*
history still lists in the API response either way (`list_chat_messages` has no limit), this
constant only caps what `build_transcript` sends to Gemini.

### `impl AiService<GeminiClient> { fn new(db, config) -> Result<Self, ApiError> }`
Fails with `ApiError::Internal` if `config.gemini_api_key` is `None`, rather than at process
startup. `Config::gemini_api_key` is `Option<String>` specifically so a missing key takes down
only the AI endpoints, not the whole backend — CLAUDE.md's Core Rules state "AI is advisory
(not required for correctness)," and a dev working only on tickets/auth/groups shouldn't be
unable to boot the server at all over an unconfigured AI feature.

### `async fn summarize_ticket(&self, user_id, group_id, ticket_id) -> Result<TicketSummaryResponse, _>`
1. `require_member` (any group member may summarize).
2. `ticket_repo.find_by_id` → `NotFound` if missing.
3. `repo.find_insight` → if present and `is_summary_fresh(ticket.content_updated_at)`, return it
   with `cached: true`. **No provider call on a cache hit.**
4. Otherwise: `provider.summarize(title, description)` → `repo.upsert_summary(...,
   ticket.content_updated_at)` → return with `cached: false`.

### `async fn analyze_ticket(&self, ...) -> Result<TicketAnalysisResponse, _>`
Same shape, against `is_analysis_fresh`/`upsert_analysis`. Independent of `summarize_ticket` —
calling one doesn't mark the other's fields as fresh (see `models.rs`).

### `async fn generate_group_report(&self, user_id, group_id) -> Result<GroupReportResponse, _>`
1. `require_group_admin` (unlike the two above — matches `docs/specification/api.md`: "Group
   Admin only").
2. `repo.find_latest_report` → if present and `is_fresh(now, REPORT_TTL_MILLIS)`, deserialize
   its `report_data` back into `ReportData` and return with `cached: true`. No ticket read, no
   provider call.
3. Otherwise: `ticket_repo.list_by_group(group_id, None, None, None)` (whole group, in memory —
   same tradeoff `TicketService::list_tickets`'s search makes) → `aggregate_stats` →
   `provider.narrate_report(&stats_summary(&stats))` → `repo.insert_report(...)`.
4. Returns using **`insert_report`'s own returned `generated_at`**, not a timestamp captured
   before the call — that earlier timestamp predates the `narrate_report` network round-trip
   (can be seconds), so using it would report an earlier time than what's actually persisted.

### `fn aggregate_stats(tickets: &[Ticket], now: BsonDateTime) -> Stats` (private)
Pure, synchronous, no provider call inside it — deliberately kept separate from the async
`generate_group_report` so it's directly unit-testable against a plain `Vec<Ticket>`. Counts
`total`/`open`/`closed`/priority breakdown/`recent_tickets_7d` (created within
`RECENT_WINDOW_MILLIS` of `now`) in one pass.

### `fn stats_summary(stats: &Stats) -> String` (private)
Renders `Stats` into the plain-text sentence `narrate_report` receives — "Total tickets: N.
Open: N. Closed: N. Priority breakdown — low: N, high: N, critical: N. Created in the last 7
days: N."

### `async fn send_chat_message(&self, user_id, group_id, ticket_id, message: String) -> Result<SendChatMessageResponse, _>`
1. `require_member` (any group member may chat, same as summarize/analyze — no admin-only
   gate). Message format validation (empty/over-length) lives in the handler only, same split
   `comment_handlers::validate_create` uses for comment content — not duplicated here.
2. `ticket_repo.find_by_id` → `NotFound` if missing.
3. Rate limit: `repo.count_recent_user_messages(user_id, now - CHAT_RATE_WINDOW_MILLIS)` — if
   `>= CHAT_RATE_LIMIT`, `ApiError::RateLimited` (`429`) **before the provider is ever called**.
4. `repo.list_chat_messages` → `build_transcript` (last `CHAT_HISTORY_LIMIT`) →
   `provider.chat(title, description, transcript, message)`.
5. `repo.insert_chat_message` twice — once for the user's message (`role: User`,
   `user_id: Some(user_id)`), once for the assistant's reply (`role: Assistant`,
   `user_id: None`).
6. Returns both, each through `enrich_chat_message`. Never cacheable — every message is a
   genuinely new request, there's no "fresh iff unchanged" check to make here the way
   `summarize_ticket`/`analyze_ticket` have.

### `async fn list_chat_messages(&self, user_id, group_id, ticket_id) -> Result<Vec<ChatMessageResponse>, _>`
`require_member` → ticket existence check → `repo.list_chat_messages` → `enrich_chat_message`
each. Whole thread, oldest-first, no pagination — same shape and reasoning as
`CommentService::list_comments`.

### `async fn clear_chat(&self, user_id, group_id, ticket_id) -> Result<(), _>`
"New chat": `require_member` → ticket existence check → `repo.clear_chat_messages`. Any member
may do this, same as any member may send a message — the thread is shared group-visible content
like comments, not privately owned by whoever started it, so there's no per-author ownership
check the way comment deletion has (`RbacService::require_owner_or_group_admin`).

### `async fn enrich_chat_message(&self, message: ChatMessage) -> Result<ChatMessageResponse, _>` (private)
Looks up the author's display name via `user_service.find_by_id` — mirrors
`CommentService::enrich_comment`. `None` for an assistant message (`message.user_id` is `None`,
nothing to look up).

### `fn build_transcript(history: &[ChatMessage]) -> String` (private)
Takes the last `CHAT_HISTORY_LIMIT` messages (`history.len().saturating_sub(...)` — never
panics on a short history) and renders them `"User: ...\nAssistant: ...\n..."`, oldest of the
kept messages first. Pure, synchronous, no provider/DB call inside it — same "kept separate so
it's directly unit-testable" reasoning as `aggregate_stats`.

### Inline tests (6)
Three on `aggregate_stats` (status/priority counting, the 7-day recency boundary, the all-zero
empty-group case) plus three on `build_transcript` (empty history → empty string, speaker/content
rendering oldest-first, capping to the last `CHAT_HISTORY_LIMIT` messages). No DB, no network.

## `ai/handlers.rs`

### `fn parse_id(raw: &str) -> Result<ObjectId, ApiError>`
Same as every other module's.

### `const MAX_MESSAGE_LEN: usize = 2000` / `fn validate_message(message: &str) -> Result<(), ApiError>`
Same limit and `.chars().count()` (not `.len()`, which counts UTF-8 bytes and would wrongly
reject valid non-Latin content under the nominal limit) as
`comment_handlers::MAX_CONTENT_LEN`/`validate_create` — a chat message is free-form user text
like a comment, no reason to give it a different cap or a different validation shape.

### Handlers

All six take `GroupScoped` — membership (or lack of it) is resolved before the handler body
runs, same "belt and suspenders" pattern as `ticket::handlers` (`03-rbac-and-middleware.md`):
the extractor proves membership, the service (for `generate_group_report`) separately upgrades
to Group-Admin.

| Handler | Extra extractors | Flow |
|---|---|---|
| `summarize_ticket` | `Path<(String,String)>` | `parse_id(ticket_id)` → `AiService::new(...)?` → `summarize_ticket` → `200` |
| `analyze_ticket` | `Path<(String,String)>` | same shape, `analyze_ticket` |
| `generate_group_report` | none — `{id}` is the only path segment | `AiService::new(...)?` → `generate_group_report` → `200` |
| `send_chat_message` | `Path<(String,String)>`, `Json<SendChatMessageRequest>` | `parse_id(ticket_id)` → `validate_message` → `AiService::new(...)?` → `send_chat_message` → `201` |
| `list_chat_messages` | `Path<(String,String)>` | `parse_id(ticket_id)` → `AiService::new(...)?` → `list_chat_messages` → `200` |
| `clear_chat` | `Path<(String,String)>` | `parse_id(ticket_id)` → `AiService::new(...)?` → `clear_chat` → `204` |

`AiService::new(...)?` is why a missing `GEMINI_API_KEY` surfaces as a clean `500` on all six
routes, rather than the process failing to start.

The `let (_, ticket_id) = path.into_inner();` pattern (dropping the first path segment in favor
of `scoped.group_id`) is the same one `03-rbac-and-middleware.md` and `07-comments.md`
describe.

### Inline tests (3)
`validate_message`: rejects empty (whitespace-only), rejects over `MAX_MESSAGE_LEN` by
**character** count, accepts within the limit. The other three handlers have nothing to
unit-test in isolation — that logic is `AiService`'s, and the wiring is proven by
`ai_api_tests.rs`.

## Routes

Registered in `server/routes.rs`, nested one level under `/ai` (distinct from the main
`/groups` scope — same `GroupScoped` extractor works under either prefix, since it reads the
`{id}` path segment by name, not by which scope it's nested in):

```
POST   /ai/groups/{id}/tickets/{ticket_id}/chat
GET    /ai/groups/{id}/tickets/{ticket_id}/chat
DELETE /ai/groups/{id}/tickets/{ticket_id}/chat
```

## Cross-module wiring

AI is the second feature (after comments) other modules cascade into:

| Caller | Calls | Why |
|---|---|---|
| `TicketService::delete_ticket` | `AiRepository::delete_by_ticket` | one ticket's insight + its chat thread |
| `purge_group_data` (`group/service.rs`) | `AiRepository::delete_by_group` | a whole group's insights + reports + chat messages |

Both follow the same child-before-parent ordering `07-comments.md` describes: the AI data is
removed before the ticket/group document itself, so a mid-failure leaves the parent still
resolvable and the cascade re-runnable.

`TicketService` and `GroupService`/`AdminService` each hold their own `AiRepository` purely to
feed these two calls, the same "held only to feed the cascade" pattern `comment_repo` and
`ticket_repo` already have in those structs.
